# MimicVerse URDF / MJCF 流水线设计

[English](design.en.md) · 中文

## 第一部分：核心原则

**单一真值、自动派生、验证后发布。**

## 第二部分：系统如何工作

```text
CAD + 机器人定义 + 规格与实测 + 用途配置
  → 冻结输入 → 规范模型 → URDF / MJCF / 网格 / 配置
  → 独立验收 → 发布
```

CAD 提供几何、装配及质量属性，机器人定义补充机械与控制语义，规格和实测提供物理与控制参数。来源冲突时，显式选择生效来源；覆盖、估计和默认值均记录依据与适用范围。
已发布工作流由稳定的 `pipeline_id` 命名；目录（`description pipeline list` / `show`）解析已发布 id 及其阶段。该身份与 `hardware_id`、工具锁和确定性 subject 摘要彼此独立。

采集将 CAD 及其完整依赖冻结为来源快照，保留原始单位、坐标系和惯量参考点，记录 CAD 与采集工具版本、配置及导出设置，并核对采集前后来源一致。原始证据保留原样，修正另记依据。

构建锁定定义、用途配置、工具及运行环境，记录版本与文件摘要。用途配置中的消费者环境按目标平台分别声明；Windows 与 Linux 的运行记录不能互相冒充。来源快照、工具和依赖包须归档或可通过不可变引用取回，才能在锁定环境中离线重建。

规范模型采用 SI 单位和统一坐标约定，明确变换方向、惯量参考点与表达坐标系，完整表达质量、质心、惯量张量、关节约束、参考坐标系、执行器、传感器和控制映射。来源实体、规范模型对象与产物对象通过稳定标识关联，每个纳入的实体实例只归属一个刚体。

视觉、碰撞和质量属性分别处理，本体与场景分开。碰撞近似记录算法、参数和误差预算，关键接触面及有依据的接触排除须在目标软件中验证；碰撞简化不改变质量和惯量。各后端从同一规范模型生成产物，对闭环、耦合、多自由度关节等明确支持范围；无法保持语义时，采用已验证扩展或停止该格式的生成。

验证从原始证据独立建立基准，核对实际产物及目标软件加载后的有效模型。在统一参考点与坐标系下比较质量、质心和完整惯量，检查物理有效性及固定体融合前后的质量属性守恒；同时检查网格尺度、放置与拓扑，覆盖全部受支持自由度的多姿态位置与旋转，核对动作与观测顺序、单位、极性和零偏。目标软件还须运行对应用途的接触、动力学或控制测试。

验收报告列出预期、已检查和缺失对象，记录误差、容差、测试工况及实际软件版本，按运动学、仿真、训练和实机控制分别判定。必需参数或证据不足，检查未运行、不支持、覆盖不足或未通过，均阻断相应用途。采样结论限于实际测试的样本和工况。

报告分别记录快照的原始采集身份及本次采集或回放方式；回放不证明当前 CAD 接口可用。合成数据不替代真实来源证据，拟合数据不兼作独立实物验收证据。

消费者选择已批准的独立参考，候选不能自行指定验收权威。可重现的一致性只证明该参考所覆盖的范围。

## 第三部分：工程如何组织

公共 `description-pipeline` 仓库分发工具。可写模型仓库以其 `main` 为起点；CAD 或模型证据需要保密时使用私有仓库。
模型仓库内的长期分支分别承担以下职责：

| 分支 | 职责 |
|---|---|
| `main` | 维护公共工具、规范与测试；发布不依赖 GitHub Actions。 |
| `feature/<硬件标识>` | 维护该硬件的定义、来源快照、生成产物和验证证据。 |
| `release/<硬件标识>` | 指向该硬件最新发布的模型提交，仅允许快进。 |

公共工具封装为一个 Python 包，提供采集、规范化、几何处理、格式生成、验证和构建能力。各阶段以显式输入输出衔接，通用规则集中维护，CLI 与 CI 复用同一套流程；调度与存储按实际规模选择。快照与规范模型采用版本化 schema，读取时检查兼容性。模型模板、Windows 部署资源和 Linux 离线入口随包分发：

```text
src/description_pipeline/          # 公共工具包
  sources/solidworks/deploy/       # worker.ps1、submit.ps1、主机配置模板、依赖锁
  deploy/linux/                    # install.sh、submit.sh
  templates/model/                # 模型模板
```

每个模型分支的根目录就是该硬件的模型工作区。建模者在 `config/robot.yaml` 中维护机器人定义；用途配置和工具锁也保存在 `config/`，其中 `toolchain.lock.json` 固定工具及依赖版本。`sources/` 保存来源快照、规格和实测证据。

构建将规范模型、URDF、MJCF 和网格分别写入 `model/`、`urdf/`、`mjcf/` 和 `meshes/`。`docs/` 保存工程决策和本地验收报告，`manifest.json` 记录输入与产物的文件摘要。模型加载入口固定为 `urdf/robot.urdf`、`mjcf/robot.xml` 和 `mjcf/scene.xml`，资源使用相对路径。

构建在独立暂存目录中完成，必需产物及检查全部完成后才提交完整候选；失败保留诊断，不覆盖已有交付。若复用缓存或历史验证结果，须核对输入、配置、工具、环境与判据，并标明复用来源。

运行职责按平台划分：

| 位置 | 职责 |
|---|---|
| Windows 工作站 | 完成 SolidWorks 或 Onshape 采集、构建、验证和 PR 提交。`submit.ps1` 提供本机入口。 |
| Linux 工作站 | 完成 Onshape 采集，或使用已冻结的 CAD 快照，独立构建、验证并提交 PR。 |
| 发布验证 | 在匹配工具锁的本机环境中，从远端重新取得精确候选并独立验收；也可交由 CI 执行。 |

默认在一台电脑完成作者流程，两端调用同一个 `description model update`。SolidWorks 的 Windows 平台限制只属于原生采集；完整快照可脱离 CAD 使用。远程采集作为可选部署，连接随作业建立与释放。

SolidWorks 原生采集需要有效许可和已登录的 Windows 桌面会话。采集端在单线程单元（STA）中串行调用 COM API，读取已保存装配及完整依赖的副本，并与用户的 CAD 会话隔离。

工具变更须用候选版本测试具有解析解的基准模型，通过错误注入检查检错能力，并在目标软件中完成回归。SolidWorks 接口须在运行 SolidWorks 的 Windows 电脑上实测。工程验收还须走通两类 CAD 来源到发布的完整链路，验证跨机离线重建及中断恢复。

## 第四部分：如何操作

以下以单个硬件型号为例，依次完成建模、验收、交付和迭代。首次建模需要明确机械定义与参数证据；完成后，日常更新使用一键入口。
规范步骤、实际入口与输出见 [SolidWorks-to-URDF 操作手册](solidworks-first-use.md)；本部分保留设计依据。

### 1. 确定目标，建立模型工作区

先确定硬件标识、CAD 装配与配置，以及模型的用途和目标软件。安装选定版本的工具，运行 `description model init`，创建模型开发分支、定义模板和工具锁。

结构设计完成后，还须把刚体划分、关节坐标与限值、参考系及参数依据落实为机器人定义。已有该硬件的定义时复用；仅更换 CAD 电脑时更新主机与来源路径，不重复创建硬件模型。

在机器人定义与用途配置中记录建模范围、必需参数、验证项目和误差容限。这些要求决定后续需要采集和补充的数据，也决定模型的验收标准。

### 2. 准备 CAD 与采集环境

核对 CAD 的装配配置、材料信息、参考姿态和外部引用。使用 Onshape 时，指定文档、装配和配置，并设置访问凭据；使用 SolidWorks 时，保存装配及其依赖文件，在 Windows 电脑上部署与工具版本匹配的采集端。

Windows 安装包包含 `worker.ps1`、`submit.ps1`、主机配置模板和依赖锁。填写 worker 配置后，执行 `Install` 安装并启动，再用 `Doctor` 检查实际装配是否可采集。采集端在空闲时切换版本，自检失败时回退。

在所选 Windows 或 Linux 电脑上安装模型锁定的完整工具，准备专用模型工作区、Git/LFS 和 GitHub 登录。首次初始化模型开发分支后，将其推送到远端。Windows 的 `submit-host.json` 只需指定本机模型工作区与用途；原生采集时保持桌面登录和 worker 可用。

维护者提供完整安装包和摘要。操作者在 CAD 电脑上完成安装与实际装配的 Doctor 检查；具体操作见[首次接入指南](solidworks-first-use.md)。

### 3. 冻结来源，确认采集范围

运行 `description source freeze`，采集选定修订和配置下的装配、几何、原始物理数据及完整依赖。工具自动检查修订、配置、实例清单和文件完整性；建模者确认纳入部件与排除项符合建模范围。

完成后的来源快照包含来源标识、修订、配置、稳定对象标识及文件摘要。依赖缺失、配置不明或采集失败时，保留诊断，修复后重新采集；只有完整快照才能进入构建。

采集作业记录作业标识和输入身份；断网或 CAD 超时后，可在输入不变的前提下重试或恢复，隔离未完成结果。清理仅针对该作业自有进程，避免影响用户的 CAD 会话。

### 4. 补齐机器人定义与参数证据

依据快照中的稳定对象标识，在 `config/robot.yaml` 中补充基座与刚体划分、关节轴与零位、限位及约束、执行器、传感器和控制映射，并选择碰撞处理策略。

CAD 已提供的数据直接引用快照；缺失或需要覆盖的物理与控制参数，从规格、标定或实测资料中补入，并记录证据与选择依据。将输入与第一步确定的用途要求逐项核对，明确尚缺的数据。

来源配置中的刚体、关节或参考系发生变化后，重新运行 `description source freeze`，使快照与最终定义一致。
每个可动关节都要登记进 `config/joint_names.yaml`：它是交付声明项（`URDF208`），`description model init`
生成的空模板在登记齐之前不会让候选通过。

### 5. 构建、审阅并修正

运行 `description build`，从机器人定义、用途配置和来源快照生成规范模型、URDF、MJCF、网格及配置，执行本地独立验证，生成本地验收报告和文件清单。

首次建模时，核对对象映射、零位和关节运动是否符合设计；后续迭代用 `description diff` 与上一次发布或候选提交比较，审阅质量属性、运动学、碰撞和接口变化——它先给一行结论（变化区域、对象数量、交付摘要是否变化），完整 JSON 报告供机器细读。检查失败时，根据报告定位来源、定义或工具问题，按第八步选择修正路径。

需要应用测试的用途，先对完整候选运行实验并保存记录，再对同一输入身份重建。仿真在 `description model update --profile simulation` 中自动执行，也可用 `description model accept` 单独运行；后续验证重放实验并比对结果。训练和实机需要各自的独立证据。未通过时保留候选与诊断。

机械运动学验收先取得已批准的外部参考，在更新、检查和发布时传入 `--mechanical-reference`，见[机械验收流程](mechanical-acceptance.md)。
它对实际产物核验身份、安装关系、有符号关节和留出运动，不提供物理或控制资格。

### 6. 一键提交候选，完成审阅

首次建模完成后，保存 CAD 或更新定义，按来源选择入口：

| 操作入口 | 命令 |
|---|---|
| Windows 部署目录 | `powershell -ExecutionPolicy Bypass -File .\submit.ps1` |
| Linux 分发包 | `bash /path/to/bundle/submit.sh --root /path/to/model` |
| 本机模型工作区，重新采集 | `description model update` |
| 本机模型工作区，来源未变 | `description model update --reuse-source` |
| 可选：Linux 连接远程 SolidWorks | `description model update --worker-host windows-cad` |

Windows 从 `submit-host.json` 读取本机工作区与用途；CLI 默认使用当前目录和 `kinematics`，可用 `--root`、`--profile` 指定。只有跨机模式需要 SSH 别名。复用模式仍须核对来源配置和快照摘要，来源改变时重新采集。

入口依次预检、冻结或复用来源、构建验证、推送候选、创建或更新 PR。同一审查分支复跑更新已有 PR；结果给出模型 SHA、PR 链接和本地验证结果。失败时保留诊断及已完成的提交状态。已分步完成构建时，可用 `description model submit` 直接提交。

审阅输入、模型差异和验证报告后，将候选合入对应模型开发分支。提交成功只表示候选已进入审阅，发布仍需下一步的独立验收。

### 7. 发布并接入使用端

候选合入对应模型开发分支后，使用锁定工具运行 `description model promote`。命令从远端将精确提交取回全新的 Git/LFS 存储，重新核对来源、实际产物、工具环境和用途证据。验收结果绑定模型 SHA、文件摘要、用途与运行环境；任何变化都须重新验收。

交付包包含模型产物、全部运行依赖、用途配置、验收报告和文件清单。全部核验通过后，才将发布分支快进到已验收的同一模型开发提交。取回或验证失败时保留现有发布，发布只声明已通过验收的用途。GitHub Actions 当前停用，不是独立验证的前提。

使用端以提交 SHA 固定模型版本。首次接入或环境变化时，运行 `description check`，复核交付完整性以及报告中的用途和环境适用范围。超出范围时，先补充相应验收；确认通过后，再使用第三部分约定的模型加载入口。

### 8. 根据变更继续迭代

后续修改从受影响的输入步骤开始：

| 变更 | 操作 |
|---|---|
| CAD、装配配置或引用变化 | 保存 CAD，更新来源配置，用一键入口重新采集、构建并提交。 |
| 机器人定义、规格或标定数据变化 | 更新定义或证据；来源配置未变时用 `--reuse-source` 重建并提交，否则重新采集。 |
| 用途、目标软件或运行环境变化 | 更新用途配置和环境记录，重新构建并完成相应用途验收。 |
| 工具或采集程序变化 | 安装新版本，用 `description tool lock` 更新工具锁，再构建；若采集逻辑修正或快照不兼容，先更新采集端并重新冻结来源。 |

新产物继续经过差异审阅、独立验收和发布。使用端需要回退时，选择仍与当前硬件、用途和环境匹配的上一已验收提交；修复后再发布新提交，发布分支仍只向前推进。
