## 一、已经确定的需求

1. 完整 pipeline 每次成功都同时交付 URDF 和 MJCF。
2. MJCF 是 pipeline 的独立阶段，可以只重跑这一阶段；不要求另建转换产品。
3. 单独重跑复用已验证的 URDF 和网格，不重新操作 CAD、不重新生成 URDF。
4. MJCF 阶段包含碰撞体简化、MJCF 编码与独立验证；失败不能获得发布资格。
5. 门户直接展示实际交付的 MJCF，支持审查碰撞体与基本仿真行为。
6. 先确定方案和计划，再执行。所有实现放在独立 worktree，开发部署使用独立端口和运行资源，不改变当前 URDF 或生产版本。
7. 工程来源、warning 保真、唯一状态权威、独立验证和正式发布权限继续遵循项目规则。此次有明确需求变化的是阶段数量和受限 MJCF 重跑入口，不扩展为任意阶段重启或历史包兼容。

## 三、阶段与职责

```text
Freeze -> Discover -> Capture -> Generate -> Verify -> MJCF -> Publish
```

| 阶段 | 本次职责 |
|---|---|
| Freeze / Discover / Capture | 原有职责保持；不为 MJCF 增加 CAD 读取 |
| Generate | 生成规范化工程模型、URDF 和实际网格 |
| Verify | 独立核验原生事实与 URDF，并提交该精确来源集合的验证决定 |
| MJCF | 消费已验证 URDF；生成接触代理、MJCF 和独立转换证书 |
| Publish | 重验两种格式各自的证据及组合字节，交付同一模型 PR |

MJCF 的独立验证使用单独模块和隔离进程，从实际 URDF、网格、策略和输出重新计算；不读取转换器的内存模型作为答案。它属于 MJCF 阶段的成功门，不额外增加用户操作步骤。

状态和重试继续由 StageApplication、FactStore、共同 stage engine、ArtifactStore 和 Airflow 负责。转换器、碰撞算法和网页均不拥有另一套任务状态。

## 四、输入、输出和摘要域

MJCF command 固定以下输入：

- 原 Generate artifact、原 Verify decision、证书和精确被验证文件集合；
- URDF、全部实际引用资源及来源绑定；
- 一份不可变仿真策略和显式覆盖项；
- 本次 converter、verifier、MuJoCo、碰撞算法的固定身份；
- 运行用途、操作者、输入闭包、契约和策略摘要。

机械事实直接读取 URDF。原生 CAD 及其证据链仍是上游最终来源；不再从历史模型、参考答案或另一份机器人参数表补值。来源元数据仅用于追踪，不得覆盖 URDF 中的机械值。

MJCF artifact 仅保存新增派生文件和其来源引用，主要包括：

```text
mjcf/robot.xml
mjcf/simulation.json
mjcf/collision/*.obj
mjcf/scene.xml                   # only when requested by the sealed policy
reports/mjcf-certificate.json
reports/mjcf-execution.json
```

视觉资源继续引用同一最终交付中的 `../meshes/`。原 URDF 和视觉网格不在 MJCF artifact 内重复封存；运行时由 ArtifactStore 物化完整的受控输入视图。接触代理是必要的新几何，具有源对象、输入摘要、算法和误差记录，不冒称原生直读值。

最终交付沿用原有输入、证据、模型、URDF、网格和工具记录，增加 `mjcf/`。最终导出包应包含完整资源，可离开平台加载；URI 引用不能仅在开发目录有效。

明确区分三个摘要域：原 URDF 被验证 subject、MJCF 转换 subject、最终组合 delivery subject。原 Verify 证书不因增加 MJCF 文件而被改写成覆盖整个交付的证书。Publish 从原始 artifact 复核 URDF 资格，核验本次 MJCF 精确引用它，并证明最终组合中的各文件与原始 artifact 一致。最终交付只有一份完整 manifest；每个阶段只有自己范围的一份证书，不持久化重复的机器人模型或第二份有效配置。

## 五、单独重跑的精确定义

门户在具有合格上游 URDF 的运行详情中提供 `Rerun MJCF`。用户可保持策略或修改碰撞精度等覆盖项；创建新的不可变请求，重跑碰撞体处理、编码和独立验证。

| 情形 | 行为 |
|---|---|
| 相同请求的网络重试 | 按原幂等键读取或恢复同一请求，不重复创建重跑 |
| 用户有意再次转换，或修改策略 | 新建受限 MJCF successor；旧结果、证书与失败历史不变 |
| 已有终态 command 被重新提交 | 复核并返回原决定，不删除决定强制再算 |
| 上游有效，原运行在 MJCF 或 Publish 失败 | 可引用仍有效的已验证 URDF 前缀；不继承失败下游 |
| 上游失败、未验证、摘要冲突或相关 effect 未决 | 拒绝重跑并显示具体来源问题 |
| 原输入、机械语义或来源规则需要修改 | 重新走正常 Freeze 流程 |
| 新转换成功 | 可继续本次下游 Publish；重新核发布目标、基线和外部效果 |

为保持现有每个 run/stage 的唯一不可变决定，采用受限的新 successor admission，复用已有 `parent_run_id`、`from_stage` 和 artifact 引用；不在旧 run 上覆盖成功或失败记录。

此入口仅允许 `from_stage=mjcf`，固定指向真正持有 URDF Verify 决定的来源 run。再次重跑仍直接引用该原始 URDF 来源，避免递归追踪历次 MJCF 重跑。接纳、claim、candidate 提交及 Publish 都重新核验来源闭包和资格，不把页面上的绿色状态或相同文件摘要当作完整证明。

源 URDF 资格仍按其来源契约与工具身份核验。此次不建设跨旧发行的通用证书或 checkpoint 兼容链；开发使用的旧产物只能作为离线样本，不能自动晋升为正式来源。

Airflow 由同一 application 入口调度新 successor，仅执行 MJCF 以及本次实际请求的下游。门户明确显示 `Reused verified inputs` 和原来源运行链接；没有执行的上游 task 不伪装为本次成功。完整初始运行仍需七阶段全部通过，重跑记录则按实际执行范围展示。

## 六、碰撞体处理

### 6.1 来源与近似边界

拟采用一个版本化自动策略：优先使用 URDF 已声明 collision；没有 collision 的 link 可从该 link 的 visual 几何派生接触代理，逐 link 明确 warning 和来源。该默认策略只有在方案获准并通过样本验收后启用；当前 URDF 原件保持不变。

visual 几何始终不参与质量、COM 或惯量估计。几何颜色、材质分区和网格文件个数不能决定物理碰撞分区。允许在同一 link 坐标系中汇集相应几何，保留组件来源与变换，不跨运动关节合并。

### 6.2 处理策略

- 已声明的简单基本体优先保留，不为统一流程增加网格化误差。
- 对凸形 mesh 使用受控顶点预算的凸接触代理。
- 对凹形 mesh 先与参考的按组件凸包基线比较；当该基线无法满足接触近似要求时评估 CoACD。每个凸分量分别成为 asset/geom，禁止合回一个 mesh 后被 MuJoCo 整体凸化。
- 控制分量数、顶点数、处理时间和内存，并独立核验最终近似质量。达到资源预算不能成为放宽误差或丢失对象的理由。
- 薄片、非水密、自相交或算法失败必须保留定位和原始错误。若算法预处理改变代理表面，应记录该变化并纳入误差检查；不得改原件、静默填洞或退成未经核验的大包围体。
- 自碰撞遵循明确的引擎规则。不能因为零位相交就自动删除碰撞对；相邻刚体过滤、显式例外与实际接触都需可解释。

按原生组件分开的凸包是参考基线；CoACD 是需要独立收益和保真证据的增强算法，基准阶段锁定实际发行与依赖。固定随机种子、处理参数和输出顺序，实际验证不同目录重复构建的可复现性。算法阈值与顶点预算属于可审计策略，不是机械事实。

### 6.3 配置和质量门

尽量只让用户调整接触近似精度等少数必要项，其余参数统一版本化。数值必须采用明确单位；不直接沿用旧项目或外部视觉对比的容差。

正式自动策略实现前，基准阶段必须确定并记录：米制误差目标、分量和顶点预算、超时与内存预算、错误分类及默认策略依据。

独立检查至少覆盖：源对象和 link 绑定、变换、代理凸性、空或退化分量、覆盖遗漏和过度包覆、关键凹槽或间隙探针、代表性接触与性能。误差报告区分抽样值和已证明界限；抽样不能冒称完整最大误差上界，CoACD 阈值也不能直接充当独立几何证明。

## 七、MJCF 转换和独立验证

保留 URDF 拓扑、关节身份、原点、有向轴、范围、质量、COM、完整惯量、visual 外观与资源变换。非对角惯量可经高精度主轴分解编码，独立验证从 URDF 重新计算并还原张量。

独立检查包含：

1. 输入闭包、工具与策略身份、实际文件摘要和包外引用拒绝。
2. link/joint 集合、父子关系、固定 frame、自由度及基座策略。
3. 零位、非零单关节和组合位姿、实际编译轴向。
4. 逐 link 与整体质量、COM、完整惯量。
5. 原 visual 几何、颜色、实例变换；collision 按本次近似策略单独核验。
6. 关节范围、被动动力学、仿真参数及任何场景派生值。
7. 必须保留的原生来源 warning，以及新增接触代理和仿真策略 warning。
8. 锁定 MuJoCo 实际加载、forward、短时无驱动步进及非有限值检查。

启用的零范围、无质量固定 frame、缺失 effort/velocity 等必须按实际原生语义处理；引擎无法支持时明确拒绝，不改范围、补惯量或隐式添加驱动器。仿真可加载不授予站立、控制、训练或硬件资格。

验证前先检查 XML 闭合语法和全部引用，再让 MuJoCo 读取资源。必要 warning 从 URDF 原样传入 MJCF，并与转换证书、门户和 PR 的对象/字段来源一致。原生缺失引用裁定继续有效，不借简化掩盖未知必需几何。

## 八、可视化方案

优先采用官方 MuJoCo WASM，加上现有 Three.js 页面框架的必要适配。浏览器加载实际交付 MJCF 和摘要绑定的资源，显示真实编译后的对象、位姿和接触几何。复用引擎和已有 UI 基础，不另写机器人运动学或碰撞引擎。

- 同一页面切换 `URDF` 与 `MJCF`；两者分别显示实际验证范围和结果。
- 提供 visual、collision 和半透明叠加；碰撞视图展示引擎实际凸分量。
- 按 link 选择，显示源碰撞来源、算法、分量数量、误差指标及 warning。
- 关节调姿与物理步进分开：滑块只改本地预览姿态；播放、暂停、单步、复位操作当前浏览器内的仿真。
- 默认暂停。显示关节轴、坐标系、质心，以及实际存在的 site 和接触点/法向；接触力只在相应动力学计算后显示。
- 交互不写交付文件、模型参数、数据库成功状态或生产运行。
- 无 actuator 的交付不显示虚假的可用驱动控制。基础地面只存在于明确策略生成的 scene 中，不为预览修改机器人零位。

优先使用单线程 WASM 和本地托管的固定资产，避免为了预览改变现有生产 SSO 或跨域头。官方 WASM 的包版本不等同于引擎版本，必须绑定实际引擎源码/二进制身份，与锁定的 MuJoCo 3.13.0 做数值与行为对照。不能仅安装 latest 后宣称一致。

正式接入前验证最大代表模型的资源加载、首帧时间、交互帧率、峰值内存、模型切换释放、损坏资源拒绝和浏览器兼容。官方绑定仍在演进，具体构建与可复用组件以该技术验证结果固定；不为采用最新 viewer 升级生产引擎。原生 Python viewer 可用作开发交叉检查，不新增常驻渲染服务。

## 九、模块和消费者改动范围

| 范围 | 计划改动 |

| 阶段契约、schemas、stages | 注册第七阶段、检查清单、证书范围和重跑身份 |

## 十二、必要验收场景

- 全流程同时交付两种格式；删改任一必需文件、伪造来源或缺 warning 均被拒绝。
- 仅重跑 MJCF，确认输入字节复用、上游未执行、旧终态未改写、下游使用新结果。
- 改碰撞策略产生新不可变请求；重复提交、并发点击和进程重启不重复决定或发布。
- URDF 验证通过而 MJCF 失败时分别展示，完整运行不得显示成功。
- 非对角惯量、非轴对齐轴、固定 frame、不同基座、零范围与缺失驱动语义。
- 凹槽、间隙、薄片、非水密、材质分区、多个组件、重复实例和不同尺度；不以模型名或数量特判。
- 原生来源不完整 warning、碰撞派生 warning、误差级别与硬件资格限制在证书、模型预览和 PR 一致。
- 超时、取消、内存限制、子进程失败和 artifact 封存失败保留原始原因，不泄漏进程或发布半成品。
- WASM 与服务端加载同一实际字节；碰撞显示与引擎接触几何一致，交互不污染交付。
- 不同绝对路径双构建、精确资源打包、固定 head 适用检查以及生产隔离验证。

只新增能证明这些行为的测试，不以测试数量为完成标准，不重复未变化且仍适用的独立证据。

## 当前执行证据（2026-10-31）

本节为开发进度，不授予正式发布资格。

- 原始参考固定在 `3f07af6f0a1cc2dde6c3b2857b381113538c87cd`。隔离副本在 MuJoCo 3.13.0 / NumPy 2.5.3 上新鲜生成、独立验证及原有十项回归通过，40 个输入文件 SHA-256 保持不变。证据位于 `.dev/m1/reference-current-engine/`。
- 迁移后的投影核心在同一参考输入上通过独立转换检查；两只支撑 site 与参考的世界位置差小于 `2e-16 m`，法向分量差小于 `2e-15`。这只证明该样本，不证明不同形状上的中心规则等价。
- 官方 WASM 3.13.0 与本机 3.13.0 使用相同中性 XML，在四个位姿及 100 步计算的所比较字段中残差为零。证据为 `.dev/m1/NATIVE-WASM-COMPARISON.json`，不宣称一般引擎等价。
- 浏览器在隔离 `127.0.0.1:8878` 加载实际参考 MJCF 和 42 个摘要核验资源；已实际操作 visual/collision/overlay 切换、0.4 rad 关节调姿、复位与 1 ms 单步。该次可见观测约 0.7–0.9 秒加载、暂停状态约 60 帧/秒、引擎 buffer 约 150 MiB；这些不是整机峰值内存或所有模型的性能保证。证据截图位于 `.dev/m1/MJCF-REFERENCE-COLLISION-FITTED.png` 等。
- 凹形中性样本的整体凸包误封槽口；CoACD 1.0.14 的三个凸分量保留了已测槽口与实体接触探针，重复构建摘要一致。更细的实验阈值产生 278 个分量，说明算法参数不能直接充当验收或性能保证。阈值尚未晋升为产品默认值。
- 参考模型的逐组件凸包最多含 1378 个顶点；后续顶点简化必须与该基线实际比较误差和收益，不能仅用中性小样本确定默认预算。
